# zz-monero (incomplete, do not deploy)

This crate uses `monero-wallet` 0.2.0 from the maintained monero-oxide project (MIT; Rust 1.89 minimum). It supplies Monero standard view-key and subaddress derivation, address parsing, scanning and transaction construction/signing. It does **not** validate Monero consensus. See https://github.com/monero-oxide/monero-oxide/tree/main/monero-oxide/wallet and https://docs.rs/monero-wallet/0.2.0/monero_wallet/ . The pinned crate and its transitive dependencies require their own license review before distribution.

`scanner` consumes blocks through the upstream API. The upstream scanner decrypts outputs but an untrusted node can omit or invent chain data. A wallet-RPC received claim, a matching header, repeated RPC answers, or an output successfully decrypted by the scanner is not independent consensus evidence. There is no verified-chain source, canonicality/reorg tracking, confirmation/unlock policy, duplicate-output-key database, change classification or deposit eligibility in this crate. No result here authorizes a mint. A durable index allocator must atomically bind the core `DepositIntent` to the subaddress before returning it; it is not wired yet.

`prepare_payout` is an offline primitive, not a safe payout workflow. Its caller must authenticate finalized assignment, select unspent unlocked owned inputs, durably reserve them, independently verify decoys and fees, and securely persist the outgoing key and exact signed bytes. These guarantees are not yet implemented. A fresh secret outgoing key is required for every incompatible transaction. The upstream constructor accepts inconsistent chain inputs; construction is not evidence of spendability. Never broadcast without rollback-resistant fencing, and never re-sign an ambiguous payment. `journaled_bytes` only validates the stored encoding and transaction ID; it neither proves its request binding nor broadcasts it.

No stagenet harness, real transaction fixture, on-chain observation, key recovery, enclave build, wallet synchronization, or end-to-end test is supplied yet. Tests use deterministic local keys only and no funds. Full chain verification and fencing remain explicit deployment gates.
