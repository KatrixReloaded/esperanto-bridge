# Explicit stagenet payout controller

`Redemptions` is a real transport/SDK/offline-signing controller for the accepted PoC assumption: **one trusted operator, one active vault process, no database rollback**. It requires `StagenetPocPolicy::accept_single_operator_single_process_no_rollback(domain)` with chain11155111 and a `TrustedStagenet` connection whose constructor verified the stagenet genesis. There is no default/environment flag silently granting payout authority. Production `VaultState::authorize_broadcast` still returns `FencingUnavailable`.

`open` takes an existing encrypted `PostgresStore`, the explicit policy, `PayoutConfig`, enclave `Identity`, and verified stagenet transport. Configuration pins fee commitment, fixed fee, network fee cap (no greater than fixed fee), per-weight daemon fee limit, at least10 Monero confirmations and the verified Zama KMS context. Payout is actual decrypted burn minus the configured fixed fee. Fee policy authenticity remains an operator responsibility; opaque on-chain fee hashes cannot prove a plaintext fee schedule.

The serialized Nitro runner shares one PostgreSQL session between the mint and payout controllers. The session holds an advisory lock in a distinct two-int keyspace and checks ownership before each journal/send. A second cooperative process cannot obtain the same lease. Session loss closes the payout path. This is **not malicious-clone, host rollback or partition-resistant fencing**. A trusted operator must never fork/replay storage or resume another live instance. Serialized encrypted state protects confidentiality/integrity, not freshness.

Run mint and redemption work in one serialized operator loop so they share the signing account's nonce discipline. Do not create another Ethereum operation while the previous operation is unresolved. The core journal separately rejects nonce reuse. Controller methods never send unless their explicit submit/broadcast method is called.

Sequence:

1. `discover(evm, from_block, to_block)` reads at most256 finalized blocks of current Bridge RedemptionRequested logs. Keep a cursor and do not advance past an unhandled candidate. Each candidate is re-read, checked eligible and fee-policy matched by `prepare`.
2. `prepare(identity, chain, evm, fhe, request)` decrypts the **actual burn** using Identity.decrypt_signer, then each of3 destination euint256 words with the same registered signer. It validates exact stagenet encoding and keys. It selects mature, confirmed local WalletOutputs, excluding every input ever reserved/spent. The real daemon supplies decoys and capped fees. Offline Monero signing stays in the enclave.
3. Reservation, fresh outgoing key and exact signed transaction are persisted atomically before claiming. The outgoing key is encrypted in the vault state, has no Debug implementation and is zeroized on drop. Different attempts cannot reuse a key or transaction. A crash before persistence cannot have released any claim or payout bytes.
4. `journal_claim(identity, evm, fhe, request, deadline, fees)` obtains the public **boolean-only Zama KMS proof**, then signs current Bridge.claim typed authorization and exact Sepolia transaction. This proof is unrelated to AWS KMS. Claim execution verifies the decryption proof on-chain. `submit_claim` records attempted-before-send and sends once. On any ambiguous result, reconcile the same hash; no replacement is constructed.
5. `broadcast(chain, evm, request)` requires successful finalized claim receipt, fresh finalized assignee=self, and fresh maturity/canonicality of reserved inputs. It persists broadcast-attempted before sending the exact recorded Monero bytes. `false` means ambiguous outcome, never permission to replace/refund/reassign. Repeated calls cannot broadcast automatically again.
6. `find_payment(chain, request, cursor)` scans at most8 sufficiently deep blocks for the exact transaction and commits canonical inclusion/depth. It returns `(found_height,next_cursor)`. The cursor is only an optimization; reset it to None after a reorg or restart. Absence does not authorize replacement or refund. Alternatively `confirm_payment(chain, request, height)` verifies an operator-provided candidate height itself.
7. `journal_settlement(identity, chain, evm, request, deadline, fees)` rechecks Monero inclusion and assignment and persists an exact signed Bridge.settle transaction. The payment commitment is salted with the private outgoing key so it does not disclose the Monero transaction hash. `submit_settlement(chain, evm, request)` rechecks payment/assignment before marking attempted and sending once. `confirm_settlement` checks successful finalized receipt and the exact assigned vault/payment commitment in Bridge state.

`pending()` returns only request IDs and `NextAction`, never amounts/destinations. It supports restart recovery from durable state; a prepared or sent operation is restored byte-for-byte. A lost claim race, cancelled request, failed transaction, stale deadline or ambiguous submission halts progress for manual reconciliation. There is no auto-refund/reassignment/replacement path. The minimal controller spends original confirmed deposits only; reusable internal-change bookkeeping is outside this one-vault demonstration.

Trust: Ethereum finalized tags and Monero canonicality, decoys, fees, inclusion and depth are observations from explicitly trusted nodes over Nym, not independent consensus verification. Local tests alone do not establish a funded payout or a live round trip. The measured optional `withdrawals` configuration enables this controller in the Nitro runner. It requires minting configuration and a restored identity, retains at least10 payout confirmations, and uses the same deployment pins and EVM fee limits as minting. Without that configuration, withdrawals remain disabled. The authenticated health response reports readiness independently for minting and withdrawals.
